### 2.3 P2 发现

**P2-1 — caller 传入的 verifier/trust 可以清掉 owner/echo blocker。**
`observation_contract.py:245-258` 只检查 verifier 的属性：

```python
core_ok = (getattr(core_verifier, "authority", None) == "core"
           and getattr(core_verifier, "production", False) is True)
owner_ok = ...
```

`validate(..., core_verifier, owner_verifier, trust, ...)`（`:306-308`）把
trust 和 verifier 作为普通参数。一个 HMAC test double 只要声明
`authority=core/owner, production=True`，且 trust 的 key_id 与它匹配，
`BLOCKED_OWNER_SIGNED_SOURCE` / `BLOCKED_PROVIDER_ECHO` 就从
`production_blockers` 消失；更彻底地，caller 可以把 trust key_id 换成
attacker key 并传入匹配的 verifier，validator 返回
`CONTRACT_SATISFIED_SYNTHETIC`（见证 f1/f2）。**但** `production_decision`
仍硬编码为 `BLOCKED_PROVIDER_SOURCE`，`production_eligible/settle_allowed`
仍 false，且 `BLOCKED_S2_OBSERVATION_FIELD / BLOCKED_COMMIT_SEAM /
BLOCKED_REPLAY_STORE` 仍在。因此这不是当前 production positive，而是
**未来 wiring 的 P2 契约边界**：若上层把“blocker 列表中无 owner/echo”当成
owner/echo 已满足，就会误读。doc `OBSERVATION-CONTRACT-2026-10-20.md:103-104`
声称“caller 不能选择信任根”，但纯函数签名本身允许；需要在 Core 集成层
用不可伪造的 keyring/trust object，或至少拒绝 caller 构造的
`Ed25519Verifier` / 非 Core 签发的 trust，并封闭 trust schema。

**P2-2 — key revocation/rotation 缺口。**
`_SOURCE_FIELDS`/`_OBSERVATION_FIELDS`（`:119-139`）没有 key epoch /
revoked 字段；`Ed25519Verifier`（`:207-242`）只有静态 `keys` 映射；
`trust` 中额外的 `revoked_key_ids` 被忽略。见证 f3：把当前 owner key 标记为
revoked 后仍返回 `CONTRACT_SATISFIED_SYNTHETIC`。doc T16
（`OBSERVATION-CONTRACT-2026-10-20.md:130`）明确把 key 轮换/撤销列为外部
Core 依赖，因此这是**已文档化残余**；生产接通前必须增加
`key_epoch`/`revoked_key_ids` 并在 verifier 中强制。

**P2-3 — missing owner/device/project 未被拒绝。**
source binding scope 用等值比较（`:382-390`），observation owner 用等值
（`:446-452`），device/project 用等值（`:484-495`），但没有
`_text`/非空约束。见证 f4：把 attempt/source/observation 的
`principal/owner_ref/device_ref/project_ref` 全部设为 `None`，validator 仍
返回 `CONTRACT_SATISFIED_SYNTHETIC`。这允许一个“空 owner/空 scope”的
签名对象满足本地 conformance；生产应先拒绝空身份/空 scope。

**P2-4 — provider echo 的 `observed_at` 未校验。**
`_ECHO_FIELDS`（`:131-135`）包含 `observed_at`，但 `:609-635` 的 echo 检查
只比较 schema/capability/adapter/verb/thread/read_path/source/client_turn_id/
matched_on/echoed_value，从未解析或比较 `observed_at`。见证 f5：
`observed_at="not-a-time"` 仍 `CONTRACT_SATISFIED_SYNTHETIC`。echo 是
Core-held provider client 的 readback；应要求可读 zoned instant、非未来、
在 max-age 内，并与 observation 的时间顺序一致。

**P2-5 — source binding 与 observation 的时间顺序未交叉校验。**
source 只检查 `issued_at <= now <= expires_at`（`:391-398`）；
observation 只检查自身 observed/issued/now 顺序（`:557-583`）；没有
`source.issued_at <= observation.observed_at` 或
`observation.issued_at <= source.expires_at`。见证 f6：source 在
observation 之后 2 秒签发，仍 `CONTRACT_SATISFIED_SYNTHETIC`。一个
observation 不应引用一个在它观测之后才签发的 source binding。

**P2-6 — source nonce / observation replay store 缺口。**
replay 只检查 `observation_id in applied_observation_ids`（`:585-592`），
而 applied set 由 caller 传入（`:306-308`）；source binding 的 `nonce` 从不
参与 replay。见证 f7（同一 source binding 下两个不同 observation 均满足）与
f8（无 applied set 时同一 observation id 再次满足；输出仍带
`BLOCKED_REPLAY_STORE`）。doc T9/T18（`:123,:132`）明确 replay store 是外部
依赖；生产接通前必须有持久 observation-id + writer-epoch replay set。
这是**已文档化残余**，不是当前 production positive。

### 2.4 为什么不给 P0/P1

- `_result`（`:267-299`）硬编码：
  `production_decision=BLOCKED_PROVIDER_SOURCE`、`production_eligible=False`、
  `send_allowed/retry_allowed/resend_allowed/settle_allowed=False`、
  `synthetic_settle_allowed=False`。没有任何返回路径能把这些变成 true。
- `BLOCKED_S2_OBSERVATION_FIELD / BLOCKED_COMMIT_SEAM /
  BLOCKED_REPLAY_STORE` 由 `_base_blockers` 无条件追加（`:256-257`）。
- 上述 P2 需要 Core 集成层错误地消费 blocker 列表、或未来 wiring 放松硬编码
  refusal，才可能变成 production 风险。当前 #365 仍是 **CODE/LOCAL/
  SYNTHETIC**，不是生产 authority。
