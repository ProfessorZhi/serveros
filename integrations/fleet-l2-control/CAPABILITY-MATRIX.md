> Generated by `python integrations/fleet-l2-control/matrix.py --render`.
> Do not edit by hand: `tests/test_l2_cloudcli_control_matrix.py` compares
> this file to the table it renders and fails on any difference.

What this answers: for each semantic an operator needs, can a Fleet caller
reach it through CloudCLI today, on what native evidence, and at which
acceptance level. It is not a claim that Fleet can "send messages"; a
message that arrives is one row of 22.

`2025-06-18`), 31 declared verbs and
29 verbatim roundtrips, captured 2026-10-27T08:12:00Z.
Carried here as shapes only (`EVIDENCE-1.41.0.json`), re-derivable with
`evidence.py`, and re-checked against the captures whenever they are on
disk.

## The two tiers

`status` is what the CODE does — every row is exercised offline by
`tests/test_l2_cloudcli_control_matrix.py`. `device` is what has actually
been SEEN of the device:

| tier | means |
|---|---|
| `OBSERVED-1.41.0` | a verbatim roundtrip in the capture exercises this shape |
| `SCHEMA-ONLY` | the verb and arguments are declared; no roundtrip called it this way |
| `NOT-OBSERVED` | neither |
| `FLEET-LAYER` | the semantic is Fleet's own; the device has no opinion |

A `SUPPORTED` row that is only `SCHEMA-ONLY` is a weaker claim than one
that is `OBSERVED-1.41.0`. Averaging the two into one green word is how a
surface comes to believe it has been tested on a device when it has been
tested against a schema.

### `send.ack` — 🟡 PARTIAL

Which native acknowledgement fields survive into a receipt?

- seen on the device: `OBSERVED-1.41.0`
- native evidence: case `send_per_run`, case `send_resident_queued`
- Fleet: `delivery_receipt` (fleet_mcp/dispatch.py), `RECEIPT_FIELDS` (fleet_mcp/dispatch.py)

**Gap.** The device answers `{deliveryId, runId, queued, queuedMessageUuid, source, blockedBy}`. A receipt keeps `run_id` and `queued_message_uuid` and drops the other four, so `queued` (was this a delivery or a run?) and `blockedBy` are not reportable. Worse, `accepted` is SYNTHESIZED — defaulted to True when the payload is silent and hardcoded True for a project — while no captured native answer carries an `accepted` key at all. `accepted: true` therefore means 'a run or queue reference exists', not 'the device said so', and a consumer that reads it as a device ACK is reading a local word.

### `run.get` — 🟡 PARTIAL

Can the state of a run be read back, by which identifier?

- seen on the device: `OBSERVED-1.41.0`
- native evidence: case `run_get_hit_completed`, case `run_get_hit_aborted`, case `run_get_delivery_miss`, case `run_get_both_ids`, case `run_get_run_hit_from_queued_send`
- Fleet: `CloudCliProvider.get_run` (fleet_mcp/providers/cloudcli.py)
- tool: `fleet_get_run`

**Gap.** The device accepts `runId` OR `deliveryId` (plus a legacy `run` alias) and answers an `idKind` saying which it used. Fleet sends `runId` only and its tool schema requires `run_id` with `additionalProperties: false`, so a delivery cannot be addressed and `idKind` never reaches a caller. The observed cases are not broken by this — a queued send answers BOTH ids — but the native half of the contract is not reflected.

### `run.identity` — 🟡 PARTIAL

Is this the same run, on the same boot, or a different one?

- seen on the device: `OBSERVED-1.41.0`
- native evidence: case `run_get_hit_completed`, case `run_get_delivery_miss`, case `run_get_legacy_aliases_accepted_run_expired`
- Fleet: `FleetService.get_run` (fleet_mcp/fleet.py)
- tool: `fleet_get_run`

**Gap.** `runId`, `deliveryId` and `bootId` are three distinct fields on the device, and every refusal carries the `bootId` it was evaluated under. A successful read passes the whole payload through, so `bootId`, `idKind`, `status` and `outcome` DO reach a caller. An ERROR envelope does not: `structured()` relays only the `code`, so a `RUN_NOT_FOUND` arrives without the `bootId` that would say 'this id belongs to a previous boot'. A restart is therefore visible only while the run still exists.

### `run.not_found` — 🟡 PARTIAL

Is a missing run a success, a transient, or a dead id?

- seen on the device: `OBSERVED-1.41.0`
- native evidence: case `run_get_delivery_miss`, case `run_get_legacy_aliases_accepted_run_expired`, case `run_get_neither_id`
- Fleet: `REMOTE_REFUSAL_CODES` (fleet_mcp/mcp_http.py)
- tool: `fleet_get_run`

**Gap.** The important half holds: `RUN_NOT_FOUND` is an exact counterpart in `REMOTE_REFUSAL_CODES`, so it is raised as a refusal and never reported as an empty successful read. The other half is dropped: the device distinguishes `reason: never_issued` from `reason: expired` and marks both `retryable: false`, and none of that survives `structured()`. A caller learns 'not found' and cannot tell 'that id was never issued' from 'it aged out' — and blind-retrying either is exactly what the `retryable: false` was there to prevent.

### `run.settled` — 🟡 PARTIAL

Is a run still executing, finished, or unknown?

- seen on the device: `OBSERVED-1.41.0`
- native evidence: case `run_get_hit_completed`, case `run_get_hit_aborted`
- Fleet: `RUN_UNSETTLED` (fleet_mcp/errors.py), `TOOLS` (fleet_mcp/tools.py)
- tool: `fleet_get_run`

**Gap.** `fleet_get_run`'s own description promises that a run not settled within the wait comes back as `RUN_UNSETTLED`. That code is declared in `errors.py` and RAISED NOWHERE — the documented behaviour does not exist. What a caller does get is the device's `status` and `outcome` passed through, which distinguishes running from terminal; the named state, and the 'still working, do not treat as failed' sentence attached to it, cannot occur.

### `stop.run` — ⛔ UNSUPPORTED

Can ONE run be stopped while the session stays up?

- seen on the device: `SCHEMA-ONLY`
- native evidence: `session_interrupt`, `session_background`, `session_cancel_queued`
- Fleet: `FleetService.interrupt_session` (fleet_mcp/fleet.py)

**Gap.** No native verb cancels a run by id. The nearest effects are session-scoped: `session_interrupt` aborts whatever is in flight in the SESSION, `session_cancel_queued` withdraws a queued MESSAGE by `queuedMessageUuid`, and `session_background` stops a background TASK by `stopTaskId`. None of the three accepts a run id, so a run-level stop tool would silently widen to a session-level one — refused here instead.

Verbs searched for and **not** declared by the device: `run_cancel`, `run_abort`, `run_stop`, `run_interrupt`.

## What is deliberately not offered

Three of the rows above are `UNSUPPORTED` because the device has no verb
for them: enumerating runtimes/agents, enumerating model ids, and
stopping one run. Each would be easy to fake — a list from the local
binding, a run-level stop built on `session_interrupt` — and each fake
would be wrong in a way the caller could only discover by acting on it. A
tool that answers "here are the models" from a config file is
indistinguishable, at the call site, from one that asked the device.
