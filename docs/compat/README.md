# Device compatibility records

This directory holds **observations of real devices**, pinned to a build, that
the Fleet connector has to be correct against. Nothing here is a design
proposal, and nothing here is generated by the connector: each file is a record
of what a device answered on a date, plus the tests that hold the answer still.

## Why records and not just tests

When a device is upgraded, the failure we care about is not "a test went red" —
it is "a verb that used to accept a parameter now rejects it, and no test was
watching". A dated record makes the diff reviewable: the capture is checked into
`tests/data/`, the tests assert its shape, and a re-capture against a new build
produces a second file to read side by side.

## Files

| File | What it records |
| --- | --- |
| [`cloudcli-windows-1.41.0.md`](cloudcli-windows-1.41.0.md) | CloudCLI 1.41.0 on a Windows workstation: the native verb surface, V1 round trips, identifier semantics, retention, and every finding. |
| `capture_cloudcli_tools_list.py` | The portable re-capture tool. Stdlib only; reads the PAT from a file named by an environment variable and never prints it. |
| `tests/data/capture-cloudcli-<ver>-tools-list-<date>.json` | The verbatim `tools/list` answer for a build. |
| `tests/data/capture-cloudcli-<ver>-v1-roundtrips-<date>.json` | The V1 calls made against that build, including the refusals. |
| `tests/test_cloudcli_windows_compat.py` | The assertions over both files. |

The 1.39.0 (22 verbs) and 1.40.0-fleet.1 (33 verbs) captures in `tests/data/`
predate this directory; they are read by the #407 line's inheritance tests and
are useful as the "before" side of a diff.

## Ownership

These records and their tests are the **L2 compatibility lane's** own new files
under issue #409. They must not become a second copy of the connector's
knowledge: where a test needs to compare the capture against what the connector
records (`fleet_mcp/cloudcli_native.py`), it **reads** that module and never
writes to it. A difference is reported as an expected failure naming the owner,
not repaired here.

## Re-capturing against a new build

```bash
# 1. the PAT lives in a file; only the file path is ever passed around
export CLOUDCLI_MCP_URL="http://127.0.0.1:3001/mcp"
export CLOUDCLI_PAT_FILE="$HOME/.cloudcli/mcp-pat-claude-code.txt"

# 2. capture the verb surface (read-only: initialize + tools/list)
python docs/compat/capture_cloudcli_tools_list.py \
    --out /tmp/tools-list-<version>-<date>.json

# 3. diff it against the previous capture, then add both files
python -m pytest tests/test_cloudcli_windows_compat.py -q
```

The capture tool prints a summary (count, names that gained or lost parameters,
tools that stopped advertising `cloudcli/handlerBound`) and no credential. If a
build no longer answers, that is a finding, not an error to hide: record the
failure mode in the dated file.

## Rules for a record

- **Pin the build.** Package version, install path, patch states and the exact
  server/protocol version. An unversioned observation cannot be compared later.
- **Quote refusals verbatim.** The error `code`, `message` and `details` are the
  contract; a paraphrase loses the vocabulary a client keys on.
- **Separate observed from inferred.** If a limit is known from a source
  constant rather than measured, say so and say which file.
- **State what was not run.** A missing `NOT_RUN` line turns "we didn't test
  this" into "this works".
- **No credentials, no unrelated user content.** Scratch sessions only; mask or
  omit anything that is not this lane's own probe text.
