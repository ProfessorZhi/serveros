# ServerOS Foundation Skeleton · 实施入口

版本：2026-09-20。性质：用户新需求对应的实施提案，不是部署完成记录。

**唯一 canonical 架构仍是 [ARCHITECTURE.md](../../../ARCHITECTURE.md)。本目录是它下面的产品设计与实施计划，不能成为第二份冲突的架构权威。** 本轮保留四平面、Core-2、唯一 resident core 和各仓库权威；不重开北京迁移，不把业务流程塞进 daemon。

## 这轮要交什么

一个可构建、可安装到隔离验证目录、可查询能力、可生成真实格式产物的 ServerOS 骨架，不是一堆空目录或声称 READY 的占位 Skill：

1. 环境底座接口、动态资源登记提案与健康观测边界。
2. ability-management 的两大家族导航、可复用 Skill 契约、版本与分发链。
3. 健康/状态卡、告警卡、恢复卡的确定性模型与可视预览。
4. 信息到交付的工作链骨架，明确先看板、后单项需求文档。
5. CC 驱动 Quay 的 Goal/AC/Task 委派链和一轮有价值的受限执行。
6. 一个供用户逐份验收的产物首页，以及 GitHub 决策/汇报交接。

## 用户已明确的产品方向

- ServerOS 让 Agent 拥有可工作的设备环境，并通过按需 Ability 推进真实工作。
- 环境内容会变化；RDC、MCP、容器、隧道及其消费者不是设计时固定清单。
- 人看的导航分为基础设施、信息到交付两大家族；物理能力身份与存储不因此重命名。
- 工作主线：授权输入/归档 → 结构化认识 → 跨项目需求看板 → 单项需求文档 → 设计与方案 → 实施/测试 → 报告与反馈。它是可选 recipe，不是所有工作必须走完的内核状态机。
- 看板像 LiteLLM 工作文档：P0/P1、项目标签、今日 1–2 项、等待与待合并；成功完成项放最底部并划线。
- Quay 是 CC 驱动的受限执行能力，不是个人工作看板的主人。Goal 与 Task 都要正确使用；不以建卡冒充运行。
- 日报有 Quay 部分，但不为凑次数制造无价值任务。
- 用户先验收产物，再逐步精修流程。普通实现选择由 CC 自主完成，不再逐节询问设计批准。

## 本目录授权的边界

本目录支持开发、隔离验证、生成预览和提交本轮代码/文档。它不是重启共享服务、开端口、建立隧道、移动云文件、启用定时外发或扩大凭据权限的许可。需要部署时集中给出一份最小变更与回退清单，未获批准保持待部署，不能伪造运行态 PASS。

实现状态必须分开报告：代码/契约、离线链路、实际 Quay 执行、隔离安装、线上切换。骨架完成不等于全部深度归档与全自动办公已经完成。
