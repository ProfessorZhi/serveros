# 健康、状态播报、告警和恢复的产品契约

这是可视呈现与适配设计，不重写 alert registry 的历史事实。ServerOS 负责观测、归属、状态与事件；能力层做确定性人话转换；飞书 renderer 只排版；投递器独立记录发送结果。[S1]

## 1. 三种卡，不做大杂烩

| 卡 | 用户问题 | 内容 |
|---|---|---|
| 健康/状态播报 | 当前还能正常工作吗？我占多少？机器与共享网关如何？ | 顶部简短健康结论 + 固定三板块 |
| 告警 | 刚发生什么、影响谁、我要不要处理？ | 最多三条高价值事件 + 关联上下文 |
| 恢复 | 哪个之前通知的问题已经恢复？ | 已通知事件的恢复事实与验证时间 |

不要另起一张重复状态大卡来充当“健康卡”。健康是状态卡的摘要与展开视图。告警卡不复制三板块，不展示全历史 OPEN/RESOLVED 数量。日报是工作报告，不混进运维告警。

## 2. 状态卡固定三板块

下例全部是布局示意，不是实时测量。实现后的预览必须带 SAMPLE 标识与源数据。

```text
Tokyo · 环境状态                 示例 / 尚未发送
环境可用性：有一项待确认        观测：部分新鲜

我的资源 · 当前账户
CPU     0.8 核 · 占整机 0.6%
内存    7.0 GiB RSS估算 · 占整机 2.8%
配额    52 / 500 GiB · 10.4%    soft 450 GiB
必要环境  已验证 5 / 6 项        [展开详情]

整机资源
CPU     2.0%                    load1 4.0 / 128逻辑核
内存    34 / 247 GiB             Swap 0.1 / 16 GiB
系统卷 /       24 / 49 GiB       数据卷 /data 236 / 4096 GiB
共享内存 /dev/shm  0.1 / 124 GiB [展开详情]

共享 AI 网关 · 与个人 container0 分开
API 就绪      已验证            数据库      已验证
最近服务调用  GPT 有成功记录；DeepSeek 本窗口无样本
本机入口      共享网关绑定的端点  负责人      Vince
                                        [展开详情]

采集时间 / 观测范围 / 数据缺口摘要
```

账户由当前 device binding/UID 解析，不写死 hwz/vince。共享网关由 service binding 选择，不因名称或 owner=ubuntu 排除，也不因为“负责人是我”获得重启权。

分母与来源：CPU 明确 cores 和占整机百分比；RSS 是估计，不承诺与 host total 精确守恒；磁盘和配额分别展示；同一文件系统不重复累加。used_percent 保留旧 hard 分母，另展示 soft/hard 比例与必要 grace。磁盘 used/total 与 df 的可用空间口径若不同，详情说明，不能默默换口径。

## 3. 每块展开什么

**我的资源**：采样区间、UID、RSS 方法、quota 类型/enforcement/soft/hard/grace、与我关联的受管 runtime 与 session，Top N 仅自己的对象；容器 root-owned 数据卷不自动算进本人 user quota，应显示不覆盖范围。

**整机**：真实挂载点、source、fstype、可用空间、inode、必要 PSI/IO/网络读数（有来源才显示）、shm 类型、采集时间。不能用“第一个不是根的挂载”猜数据盘，不能展开他人 cmdline、凭据或私有目录。

**共享网关**：服务身份、owner/maintainer/授权边界、app/db 状态与独立数据卷、liveness/readiness、重启计数、版本、最近真实流量窗口/样本数/成功失败/延迟、模型族映射的可信来源。health 200 不证明模型完成请求；无样本显示“未验证”，不刷绿色。私有 container0 单独在我的 runtime 详情，不冒充同事共享入口。

从东京 localhost 的检查不能证明手机/Windows/容器网络的访问路径。外部访问没有探针就显示未验证，不为验证而创建隧道或付费模型请求。

## 4. 告警必须经过语义处理

```text
Alert Fact + 现有生命周期事件 + subject resolver + 定义目录
                          ↓
      确定性 presentation model
                          ↓
                  飞书 / CLI / HTML
```

最小 presentation：发生了什么、对象显示名、事件类型、原严重度、影响、确定性/证据质量、建议、首次/最近观测、持续时间、引用。不能靠 LLM 自由生成根因，不能把重启失败自动解释成网络故障。

示例：

```text
需要关注 · 远程控制通道暂时无法确认
对象：本节点的 Remote Control binding
已知：本地进程仍在；最近一次远端在线观测已过期。
影响：现在不能确认外部 Agent 能否接入；不等于进程已停止。
建议：检查远端连接与认证状态；本卡不会触发重启。
观测于 2 分钟前 · 状态未知
[证据与详情]
```

ORPHAN_PROCESS_TREE 若只证明“未关联受管工作”，显示“有一组进程尚未归属”，不声称危险、泄漏或必须杀掉；owner 未知本身不应被 UI 擅自升级成 Critical。原规则严重度不合适时开独立规则修正，不由 renderer 偷改；当严重度高但事实仅是待核实，详情同时说明两者。

发生过程的频率只能按有据时间窗描述；只有 lifetime count 时写“累计再次出现”，不能编造“过去两小时重复 N 次”。没有影响证据时明确“影响尚未确认”。

## 5. 生命周期与投递

NEW/ESCALATED/REOPENED/RECOVERED 采用现有 ServerOS 事件来源，不重新比较一个简化快照来制造事件。

- 发送：新的需处理异常、升级、值得关注的复发，采用去抖/迟滞/冷却和预算，不能对每个 5 秒采样发卡。
- 根因与依赖相关的事件优先合并；保留原 alert refs，不删除账本来降噪。
- 已发送的问题后来有肯定恢复证据，才发恢复；观测失联或权限丢失不是恢复。
- 既有积压不冒充 NEW；持续故障的提醒按明确策略，不静默丢掉重要事件。
- 只因账本总数或游标变化不发通知。投递失败不消耗事件；使用现有幂等/receipt，不能同时保留两套定时发送器。
- UI 点击只能产生已认证、带版本与范围的意图。发送/重试/打开详情不等于批准 kill/restart/cleanup。

默认卡面移除：完整 code/subject URI、generation、baseline、全历史恢复数、长免责声明。详情保留原 code、severity、scope、source/freshness、证据 locator、已支持的查询操作；没有真实动作接口的按钮不可做成可点击假按钮。

## 6. 视觉要求与验收

三板块用统一标签、短行、清晰间距；颜色只编码语义，文字始终说明状态。未知用中性而非正常绿；避免反引号和转义下划线泄漏到卡面；手机不使用宽表格。

可用飞书官方 collapsible panel 等真实组件；按当前 card schema/SDK 校验，不从草图发明 JSON 属性。[S11]

交付同一 renderer 生成的 JSON 与 HTML/可视预览，覆盖：正常、部分未知/过期、单个严重异常、观测器失败、混合异常+恢复、仅恢复。手机窄屏约 390px 与桌面预览均无横向溢出；正常卡三板块首行可辨；单告警第一屏直接看见事件/对象/动作，不先滚过一整机指标。

视觉预览不是飞书投递证据。当前 API/App1 客户端的实际显示待用户批准后发送合成测试卡回读；生产定时器切换独立审批。不能把回读旧幂等 message_id 说成新消息到达。
