文档应成为显式的高优先来源 binding，不能只存在于聊天链接或人工记忆里。初始消费前读取准确 revision，增量时保留内容及相关富文本状态；B1 的精确版本与 coverage 必须传到 B2 和 B3。

## 2. 状态与富文本必须一起读

除了标题和正文，还应保留：章节归属、删除线、下划线、勾选状态、优先级标题、相关链接和必要批注。这些信息参与来源语义版本判断；只抽纯文本可能把已解决问题重新解释为待办。

| 来源信号 | 处理方式 |
|---|---|
| 进入“已完成”区域，整项标题有删除线，正文有解决结论 | 形成 `completed_in_source` 的可追溯观察，提取适用版本/路由/范围；更新旧认识与候选展示 |
| 删除线只覆盖局部文字 | 可能是文字修订，不推断整个需求完成 |
| 只有下划线、链接样式或粗体 | 不据此判完成；结合正文/章节或列入理解缺口 |
| 从已完成移回待办，或新聊天有相同问题的新证据 | 判断回归、新范围或状态冲突，保留旧完成历史，按对应 owner 决定 reopen/新提案 |
| 原文条目消失 | 记录不可见/撤回/覆盖缺口，不自动视为完成或取消已接受决定 |

`completed_in_source` 是来源观察，不是 Work Engine CLOSED。来源已完成且与内部 AC 一致时，按既有完成政策核验后收口；内部还欠发布或其它 AC 时，显示“来源已完成 / 内部待验的具体项”，不再把整个旧问题当新需求提出。

文档和聊天发生冲突时，结合精确版本、发言人的业务职责、适用范围与时间处理。文档是重点参考，不是无条件压过最新明确决定；较新的闲聊也不会自动推翻正式完成结论。

## 4. 认识与需求的去重键

先按 Source task 的稳定对象/块定位、目标与范围映射已有 Requirement/Item；保留标题别名、来源版本和跨来源链接。不要只按“WorkBuddy”或相似标题合并。

对历史完成项：
1. 找到旧 Claim、待对齐候选与已存在 Item 的关联；
2. 写入来源完成和结论范围的纠正/替代关系；
3. 不重复生成同一目标的新候选，也不自动加进 Focus；
4. 已接受的 Work 由 Work owner 对 AC/交付状态作处理，保留证据；
5. 新证据表明确有复发时，形成有来源的回归/重新打开提案。

普通状态对账、重复候选折叠与认识纠正应在已有授权内批量完成；只把真正的语义冲突或新取舍交给用户。

## 5. 自有需求看板的格式

采用一篇长期维护的看板，借鉴源文档的层级与阅读习惯：

```text
当前 Focus（跨项目共 0–2）
待对齐（只保留独立目标、变化与冲突）
未完成
  P0：标题
    目标 / 当前状态 / 下一步 / 来源与证据
  P1…P4：同样形式，按真实需要显示
已完成（默认折叠）
  删除线标题 + 原优先级 + 解决结论/适用范围 + 交付链接
```

保留来源优先级与内部已接受优先级的出处。没有优先级时显示“待排”，不从函数名、旧标题碎片或 Item state 猜一个 P 值；源文档明确的 P0/P1 标记可作为带来源的输入，经 B3/B4 对齐进入正式看板。

源文档的服务器说明、生产访问细节不复制到需求看板。正文以短需求说明、状态和关键链接为主，机器字段/完整日志折叠到证据入口。移动端优先，避免把 JSON 或内部实现术语塞进主阅读面。

采用“样式参考＋本地 profile”，不整篇镜像原文。更新自己的文档也需保留人工批注，使用条件写与 readback。展示完成由正式状态驱动；不能只给标题加删除线就声称内部交付已验收。
