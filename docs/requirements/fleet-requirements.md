# Fleet 需求清单

- **状态：** 第一轮对齐完成（2026-11-13）。§11 的 7 个问题已有答案，写进了对应需求
- **本文是什么：** Fleet 全部需求的唯一编号清单。每条需求都有编号、验收标准、自动化档位和当前状态。细节和背景在同目录的其他文档里，这里只放结论和链接。
- **权威：** 需求只在 Git 里存这一份。飞书云空间里的「需求看板」和 GPT 在聊天里渲染的表格都是从本文生成的视图，不能在视图上改需求（见 [A-3](#a-对齐与需求看板)）。

## 0. 怎么读

**状态**

| 标记 | 含义 |
|---|---|

| 部分 | 有实现，但没覆盖三台设备，或缺验收 |

| 待定 | 需要 Owner 先拍板；拍板结果记在 [§11](#11-对齐结论2026-11-13) |

**自动化档位**

| 档位 | 含义 | 举例 |
|---|---|---|
| 全自动 | 只读或可撤销，直接做，留记录 | 归档、重算认识层、统计、生成视图 |
| 自动＋通知 | 低风险写操作，做完通知 Owner | 清理超过期限的 tmp、删除已合并的分支 |

**分工：** GPT 和本地 DeepSeek 采集信息、做对齐；云端 Claude 决策并实现代码，CI 绿即合并；各设备的本地 Claude Code 负责部署。

## 1. 总原则

| 编号 | 原则 |
|---|---|
| P-1 | **准确度优先于自动化程度。** 每条事实都带出处（哪条消息、哪个文件、哪条命令）和时间；没有出处的话不进认识层。 |
| P-2 | **分层只能往上推导。** 原始层只存事实、零结论；认识层可重算、可追溯到原始层；需求层只收 Owner 确认过的；条目从需求拆出。下层不能写上层的结论。 |
| P-3 | **一个事实一个权威。** Git 是需求、项目、编号、报告的权威；飞书是单向发布的视图；设备的运行事实以设备回读为准。 |
| P-4 | **agent 只加载需要的上下文。** 认识和需求按小卡片组织，每张卡有「当前真相」和版本；不把整仓库塞进上下文。 |
| P-5 | **所有执行都有界。** 外部操作有超时、整体期限、进程树回收、单实例；重负载有内核内存上限（见 [性能需求](fleet-efficiency-performance.md)、production-observation 资源底线）。 |
| P-6 | **一切可观测。** 链路的每一跳有时间戳；断在哪一跳能看见；状态不明不报成功。 |
| P-7 | **幂等。** 重试不重复执行、不重复发卡、不重复归档。 |
| P-8 | **工作流是循环，不是瀑布。** 认识 → 需求 → 调研 → 设计 → 开发 → 测试 → 报告，任何一步都可以回到前面，也可以派生新条目。 |

## 2. 工作流模型

```text
信息采集 → 结构化认识 ──┐
   ↑                    ↓
   │       需求 → 调研 → 设计 → 开发 → 测试 → 报告
   │         ↑       ↑      ↑      │      │      │
   │         └───────┴──────┴──────┴──────┘      │
   └────────────── 交付后的观察与新信息 ───────────┘
```

| 层级 | 例子 | 说明 |
|---|---|---|
| 项目 | litellm，前缀 `LIT` | 登记在 hwz-records `ops/workspace/serveros/projects.yaml`；一个前缀只属于一个项目 |
| 条目 | `LIT-0222` | 一件具体的事；kind ∈ feature / bug / test / investigation / analysis / report / deploy / ops / support / decision |
| 活动 | registration → G0 盘点 → G1 复现 → G2 修复 → G3 测试 → G4 A/B → G5 交付 | 条目内的依赖图（`plan.yaml`），不是固定流水线 |
| 运行 | `RUN-0007` 失败 → `RUN-0008` 通过 | 每个活动可有多次运行，失败的也留记录 |

## K. 采集与结构化认识

| K-2 | **其他来源归档**：GitHub（Issue、PR、提交）、fleet-journal、设备采集报告 | 同 K-1 | 全自动 | 部分 |
| K-3 | **归档自检**：任一来源超过阈值没更新，飞书提醒 Owner | 停更一个来源，阈值内收到提醒 | 全自动 | 缺 |
| K-4 | **结构化认识**：从原始层每天重算 `information/understanding/` 的卡片：人与职责、项目、系统与设备、话题、决定 | 每张卡有：当前结论、出处、最后核实时间、置信度；重算只提交差异 | 全自动 | 部分 |

| K-6 | **上下文供给**：agent 按任务取相关的认识卡，而不是读全仓 | 一次派活附带的上下文 ≤ 约定上限，并列出用了哪些卡 | 全自动 | 缺 |
