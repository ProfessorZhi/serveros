## 1. 总原则

| 编号 | 原则 |
|---|---|
| P-1 | **准确度优先于自动化程度。** 每条事实都带出处（哪条消息、哪个文件、哪条命令）和时间；没有出处的话不进认识层。 |
| P-2 | **分层只能往上推导。** 原始层只存事实、零结论；认识层可重算、可追溯到原始层；需求层只收 Owner 确认过的；条目从需求拆出。下层不能写上层的结论。 |
| P-3 | **一个事实一个权威。** Git 是需求、项目、编号、报告的权威；飞书是单向发布的视图；设备的运行事实以设备回读为准。 |
| P-4 | **agent 只加载需要的上下文。** 认识和需求按小卡片组织，每张卡有「当前真相」和版本；不把整仓库塞进上下文。 |
| P-5 | **所有执行都有界。** 外部操作有超时、整体期限、进程树回收、单实例；重负载有内核内存上限（见 [性能需求](fleet-efficiency-performance.md)、production-observation 资源底线）。 |
| P-6 | **一切可观测。** 链路的每一跳有时间戳；断在哪一跳能看见；状态不明不报成功。 |
| P-7 | **幂等。** 重试不重复执行、不重复发卡、不重复归档。 |
| P-8 | **工作流是循环，不是瀑布。** 认识 → 需求 → 调研 → 设计 → 开发 → 测试 → 报告，任何一步都可以回到前面，也可以派生新条目。 |

## 2. 工作流模型

```text
信息采集 → 结构化认识 ──┐
   ↑                    ↓
   │       需求 → 调研 → 设计 → 开发 → 测试 → 报告
   │         ↑       ↑      ↑      │      │      │
   │         └───────┴──────┴──────┴──────┘      │
   └────────────── 交付后的观察与新信息 ───────────┘
```

| 层级 | 例子 | 说明 |
|---|---|---|
| 项目 | litellm，前缀 `LIT` | 登记在 hwz-records `ops/workspace/serveros/projects.yaml`；一个前缀只属于一个项目 |
| 条目 | `LIT-0222` | 一件具体的事；kind ∈ feature / bug / test / investigation / analysis / report / deploy / ops / support / decision |
| 活动 | registration → G0 盘点 → G1 复现 → G2 修复 → G3 测试 → G4 A/B → G5 交付 | 条目内的依赖图（`plan.yaml`），不是固定流水线 |
| 运行 | `RUN-0007` 失败 → `RUN-0008` 通过 | 每个活动可有多次运行，失败的也留记录 |

## 3. 设备角色与分层（Owner，2026-11-14；2026-11-18 更新）

三台设备不要求一致。完整工作流只在东京；另外两台按条目编号接活、交结果，结果和产物的指针回写东京与 hwz-records，自己不保存工作流状态。

| 设备 | 角色 | 跑什么 | 不跑什么 |
|---|---|---|---|
| 东京 | Hub + 工作流中心 + 主开发机 | Fleet Hub、监控与飞书播报、采集与结构化认识、需求与条目、每日对齐、fleet-journal；主要的代码开发 | — |
| A6000 | GPU 计算节点 + **主力查日志** | **LLM Lab**：GPU 资源管理、模型部署与推理、模型服务与门户（llmlab-agent、llmlab-bff、门户、strata-public / Caddy，数据在 `/srv/llm-lab`）；个人项目；**生产日志的查询与分析**（生产只读通道 `fj-prod-broker`、`litellm-log-analysis`） | 完整工作流 |
| FJPCOS（Windows） | Windows 客户端节点 | **真实客户端测试**（飞书、ChatGPT、浏览器、Windows 原生客户端）；只有 Windows 侧才有的日志通道，作为查日志的备用；个人项目 | 完整工作流 |

**查日志的主路径（2026-11-18）：** 指挥（GPT 或飞书）→ Fleet → A6000 经生产只读通道查询 → 子集落在 A6000 `work/logs/<日期>` → `litellm-log-analysis` 分析 → 报告进 hwz-records 对应条目 → 卡片通知。FJPCOS 只在需要 Windows 侧通道或复现客户端问题时参与。

**设备侧分四层（从下到上）：**

| 层 | 是什么 | 三台是否一样 |
|---|---|---|
| serverosd | 底座：资源采集（core-lite）、状态发布、连接 Hub、事件推送（D-4，Rust）。不放业务逻辑 | 一样 |
| serveros 能力族 | 核心包（本机说明、能力发现、有界执行、条目、目录治理）+ 角色包；装了什么以 ability-management 登记为准并由设备读回（C-6） | 核心包一样，角色包按设备 |
| 连接层 | 「Agent 接入接口」（D-2）：Fleet 用它驱动设备上的 Claude Code / Codex。目前唯一实现是 CloudCLI，可替换 | 接口一样 |
| 指挥侧 | ChatGPT / claude.ai / 各设备 CC 会话 / 飞书管家；指挥侧 Skill = 精简核心 + 按需业务知识包（D-6） | — |

**角色包（C-6）：** 东京：工作流、飞书、记录、fleet-journal；A6000：GPU 与模型部署、日志分析、LLM Lab 守护；FJPCOS：客户端测试、Windows 运维、Windows 侧日志通道。

- A6000 上的 LLM Lab 是在用的服务：Fleet 的任何改动（目录、清理、资源告警、重启）都不能影响它；资源画像与告警（O-4）要把 GPU 显存、模型进程算进去。
- 目录治理（R 组）三台都做，规则相同、分区按设备（R-1）；个人项目只登记不动。
