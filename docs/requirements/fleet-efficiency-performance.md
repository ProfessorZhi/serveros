# ServerOS Fleet 效率、性能与执行可靠性需求

- **状态：** 需求收集稿，待 Owner 确认；不是实现设计，也不代表已实现或已验收
- **日期：** 2026-11-13
- **范围：** ServerOS Fleet 的节点运行时、任务调度、进程编排、同步任务、通信与控制路径
- **需求来源：** Owner 对效率/性能优先级的明确要求，以及 Windows Secrets Sync 阻塞事件
- **关联实现：** `distribution/keycenter/`、`native/node-core/`、`fleet_mcp/node/`

## 1. 核心目标与优先级

ServerOS Fleet 的**效率与性能必须从项目起点就是核心工程目标**，而不是功能完成后的补救性优化。它们是持续迭代、架构选择、技术选型和验收中的一等要求。

目标不是单纯追求某个微基准的速度，而是让 Fleet 在真实设备、真实负载和长期运行条件下：

1. **响应快：** 启动、任务调度、节点通信、状态采集、同步和恢复的延迟可测量、可控制。
2. **资源省：** CPU、内存、磁盘 I/O、网络流量、进程/线程数量和后台空闲开销保持合理。
3. **吞吐高：** 并发任务增加时，系统能有效利用设备资源，不因不必要的串行、重复启动或进程开销形成瓶颈。
4. **生命周期可靠：** 超时、取消、失败、重试和恢复都有明确边界，不遗留孤儿进程、不无限等待、不无限累积任务。
5. **迭代成本低：** 性能问题可以通过指标、基准和剖析快速定位；优化可以小步验证，不依赖猜测或大规模重写。

性能优化不能以牺牲正确性、安全性、数据完整性或可运维性为代价。性能、可靠性和安全性需要共同进入验收标准。

## 2. 技术选型原则：积极评估 Rust，按证据落地

Owner 明确提出：Fleet 中有不少环节可以考虑使用 Rust；效率和性能是技术演进的重要依据。

据此记录以下要求：

- 对高频、常驻、并发密集、CPU 密集、I/O 密集、进程管理或低延迟路径，**必须主动评估 Rust**，不能因为现有实现使用 Python 就默认继续使用 Python。
- Rust 是性能敏感模块的优先候选技术之一，尤其适用于需要低资源开销、明确并发控制、内存安全和可控执行生命周期的组件。
- 语言选择必须由实际工作负载和基准测试支撑：比较延迟、吞吐、CPU、内存、启动时间、部署体积、跨平台行为和维护成本。
- 不要求为了使用 Rust 而全仓库重写。现有 C++ 原生模块可以继续承担适合它的底层职责；Python 可继续用于低频控制逻辑、脚本和集成层，前提是它没有成为已测量的瓶颈。
- 对性能关键路径，优先减少不必要的进程启动、重复解释器启动、跨语言往返、同步阻塞和无界缓冲；具体采用何种实现方式由后续设计与测量决定。
- 任何语言迁移都必须保持现有安全边界、协议兼容、可观测性和跨平台验收能力。

**本节是技术选型要求，不是当前 Rust 改造清单。** 是否迁移某个模块，必须先有基线、瓶颈证据和收益评估。

## 3. 全局非功能需求

### 3.1 可测量、可设预算

每个关键运行路径都需要有可复现的性能基线，并逐步建立预算。至少覆盖：

- 延迟：启动时间、任务排队时间、执行时间、端到端完成时间；按场景记录 P50/P95/P99。
- 吞吐：单位时间处理的任务数、并发任务数、同步完成率。
- 资源：CPU 时间/利用率、常驻内存与峰值内存、磁盘读写、网络字节数、进程/线程数量。
- 稳定性：超时率、失败率、重试次数、取消耗时、孤儿进程数、重复执行数、恢复时间。
- 空闲开销：无任务时的 CPU、内存、唤醒频率、轮询与网络活动。

具体数值预算目前**待测量和确认**，不能在没有基线时编造统一阈值。后续按组件关键程度、设备能力和真实负载设定预算，并把预算纳入 CI、基准测试或设备验收。

### 3.2 所有外部操作必须有界

任何可能阻塞的外部操作都必须有明确的时间和资源边界，包括但不限于：

- Git、SSH、网络连接、远程命令；
- 子进程、脚本和外部可执行文件；
- IPC、管道、socket、文件锁；
- 任务队列、重试、等待和健康探测。

要求：

1. 区分连接超时、单步超时和端到端绝对 deadline；不能只设置连接超时就声称整个操作有界。
2. deadline 到达后，必须触发可验证的取消与回收流程。
3. 取消必须覆盖由该任务拥有的子进程/后代进程；不能只结束包装器或父进程后就把任务标记为完成。
4. 对不能确认是否已执行完成的外部副作用，状态必须保留为未知并先对账，不能盲目重试。
5. 输出、缓存、队列和并发数必须有上限，避免异常任务耗尽内存或系统资源。

### 3.3 单实例与并发治理

- 同一逻辑任务在同一设备/用户作用域内必须有明确的 single-flight 或等价互斥保证。
- 调度器的“忽略新实例”不能替代应用层对实际执行者、进程树和锁生命周期的治理。
- 上一轮执行未真正结束时，不得因父进程退出、任务状态重置或调度器误判而启动重复执行链。
- 锁必须与真实任务生命周期绑定；异常退出后应能安全释放或通过可验证的恢复协议处理，不能留下永久死锁，也不能因锁过期而并发执行。
- 并发上限、排队策略、过载拒绝和退避行为必须明确，不能让高频触发形成资源雪崩。

### 3.4 进程生命周期必须闭环

对每个由 Fleet 启动或管理的任务，必须能够回答：

- 谁创建了进程，谁拥有它；
- 子进程和后代进程有哪些；
- 谁负责发送取消/终止；
- 如何等待进程退出并回收句柄/资源；
- 如何取得真实退出码和最终结果；
- 进程无法确认退出时，如何报告和阻止重复启动。

任务状态必须反映真实执行结果。包装器启动成功不等于工作成功；父进程退出不等于后代进程已退出；超时发生不等于副作用一定没有发生。

### 3.5 跨平台行为一致

Windows 计划任务、Linux systemd timer/service，以及其他运行环境应遵循统一的任务生命周期语义：

- 同一逻辑任务的 deadline、取消、并发、退出码、日志和恢复语义一致；
- 平台差异由受测的适配层处理，不应形成一边有界、一边无限等待的行为分叉；
- 必须分别验证真实操作系统行为，不能把 Linux 测试或 Hosted Windows 测试冒充目标设备验收。

### 3.6 可观测与可诊断

每次关键执行至少记录：

- 稳定的 task/run ID、任务类型、设备与执行身份；
- 开始时间、结束时间、耗时、deadline、退出码和最终状态；
- 超时、取消、重试、锁等待、并发拒绝等结构化原因；
- 进程树回收结果和可安全披露的资源指标。

日志不得记录密钥、令牌或其他 Secret 值。诊断信息应足以定位阻塞阶段，但不得以无限制的 stdout/stderr 捕获造成内存增长或敏感数据泄露。

## 4. Windows Secrets Sync 事件：首个具体需求案例

### 4.1 事件背景

2026-11-13 的问题排查记录显示，Windows Secrets Sync 的执行链为：

```text
Task Scheduler: \\ServerOS\\ServerOS Secrets sync
  -> wscript.exe run-hidden-wait.vbs
  -> powershell.exe sync-secrets.ps1
  -> python.exe serveros_secret.py sync
  -> git.exe pull --ff-only
  -> ssh.exe vince "git-upload-pack 'serveros-secrets.git'"
```

排查记录指出 Git Pull 曾阻塞在 SSH 子进程；同一时段手工执行 `ssh vince "echo SSH_OK"` 成功。这只能说明该次简单 SSH 探测成功，不能证明 Git 的 SSH 调用不存在间歇性阻塞或上下文差异。

仓库当前实现中可确认的配置/代码事实：

| 位置 | 当前可见事实 | 需求含义 |
|---|---|---|
| `distribution/keycenter/windows/register-sync-task.ps1` | 默认每 5 分钟触发；`MultipleInstances=IgnoreNew`；`ExecutionTimeLimit=3 minutes` | 触发间隔、任务期限和真实进程生命周期必须统一设计 |
| `distribution/keycenter/serveros_secret.py` | `_run()` 使用同步 `subprocess.run`，没有显式 timeout 参数；`sync()` 的 Git Pull 通过 runner 调用 | 外部命令必须有端到端 deadline 和取消/回收语义 |
| `distribution/keycenter/windows/sync-secrets.ps1` | 同步调用 Python 并收集输出，没有独立的进程树 deadline 管理 | PowerShell 包装层不能成为生命周期治理的缺口 |
| `distribution/keycenter/windows/run-hidden-wait.vbs` | 隐藏启动并等待子命令返回 | 等待退出码是必要的，但还不足以证明后代进程会被完整回收 |

当时的排查将“任务执行期限到达后只结束父进程、后代进程继续运行，下一轮再产生新的执行链”作为根因解释，并报告出现多套残留链。**这一具体 Task Scheduler 终止语义和现场残留数量仍需在目标 Windows 主机上用进程树证据复核**；本需求文档不把未经独立复核的解释写成平台保证。

### 4.2 本事件导出的强制要求

- Git Pull / SSH 必须具有明确的连接超时与整体 deadline；阻塞不能无限持续。
- 超时后，必须结束并回收该次同步拥有的完整进程树，而不只是 wscript、PowerShell 或 Python 的某一层。
- 同一设备上的 Secrets Sync 同一时刻最多存在一个有效执行实例；调度器、脚本和 Python 入口之间不能各自假设其他层已经完成互斥。
- 单次同步必须返回真实、可追踪的成功、失败、超时、取消或结果未知状态。
- 失败不能导致下一轮不断叠加孤儿进程；下一轮应在确认上一轮已结束或进入受控恢复状态后执行。
- 正常同步应尽量减少启动和重复工作开销；没有变化时不应触发不必要的下游重启。
- 日志应能指出卡在 Git、SSH、解密、文件写入还是下游重启阶段，并保持只记录 Secret 名称/元数据，不记录 Secret 值。
- 该案例必须同时验证 Windows 计划任务路径与底层 Python CLI 路径；仅测试某一层不足以验收整条执行链。

### 4.3 本案例验收标准

1. 能在隔离测试环境中稳定模拟 Git/SSH 长时间无响应。
2. 在调度周期继续到来时，不产生第二套并行同步进程树。
3. deadline 到达后，所属进程树在规定的取消宽限期内退出并完成回收；若无法确认回收，系统必须保持明确的异常/未知状态并阻止重入。
4. 任务记录的终态与实际子进程结果一致，退出码不被包装器吞掉或伪造。
5. 阻塞解除或故障恢复后，后续同步能够正常执行，不依赖人工逐个清理孤儿进程。
6. 连续运行和故障注入测试中，进程数、内存和句柄数量不随调度周期持续增长。
7. 验证正常路径的耗时、CPU、内存和进程启动开销，并将结果作为后续优化基线。
8. 验证 Secret 值不会进入 stdout、stderr、任务历史或日志。

## 5. 性能优化的迭代要求

后续每个性能优化工作包都应遵循同一闭环：

1. **定义场景：** 指明设备、负载、输入规模、并发数和运行时长。
2. **建立基线：** 测量延迟、吞吐、CPU、内存、I/O、网络和错误率。
3. **定位瓶颈：** 使用 profiling、trace、系统计数器或可复现的测试，不凭语言偏好猜测。
4. **提出最小改动：** 优先消除算法复杂度、重复工作、无界等待和资源泄漏；必要时再替换实现语言或运行时。
5. **对照验证：** 在同一环境、同一负载下比较优化前后数据。
6. **防止回退：** 对关键指标建立基准测试或回归阈值；记录硬件、OS、版本和测试条件。
7. **真实设备验收：** Hosted CI、模拟环境、交叉编译与真实设备结果分开标记。

性能报告不能只写“更快”或“资源更少”，必须给出测量条件和对照结果。优化收益应同时考虑运行成本、复杂度、可维护性与部署成本。

## 6. 当前范围与明确不包含的事项

本文件只收集和定义需求，不授权任何设备操作或代码变更。

当前范围：

- ServerOS Fleet 的整体效率、性能和执行可靠性要求；
- 调度、子进程、外部命令、网络调用、常驻进程与同步任务；
- Rust/C++/Python 的性能导向选型原则；
- Windows Secrets Sync 作为第一个具体问题案例；
- 后续性能基线、验收和迭代优化要求。

当前不包含：

- 直接修改 Python、PowerShell、C++ 或 Rust 实现；
- 将现有代码整体迁移到 Rust；
- 修改真实设备上的计划任务、进程、服务、密钥或权限；
- 部署、重启、清理生产/共享设备；
- 在缺少基线时预设未经确认的性能数字。

任何实现、设备执行或生产变更都应作为后续独立工作项，根据其具体风险和授权范围推进。
