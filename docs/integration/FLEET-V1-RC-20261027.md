## 4b. Integration-level contract conflicts found in the combined tree

These are not merge conflicts. They are two PRs that each pass their own tests
and disagree with each other **only when they sit in one tree** — which is the
reason for building the tree at all.

### P0 — `milestone_kind` is two mutually exclusive vocabularies

| Source | Values |
|---|---|
| #422 `docs/architecture/FLEET-V1-MILESTONE-DELIVERY.md` (line 213) | `DISPATCH_ACK` · `RUN_ENDED` · `CI_PASSED` · `QA_ACCEPTED` · `FEISHU_DELIVERED` (line 215 explicitly forbids `OWNER_READ`) |
| #423 `integrations/fleet-v1-milestone-notify/milestone_notify.py` | `RUN_COMPLETED`, `CI_PASSED`, `PHASE_ACCEPTED`, `PR_ACCEPTED`, `TASK_COMPLETED` |

Only `CI_PASSED` appears in both. #423 does not reference #422's contract at all.
Both PRs present themselves as the single authority for milestone kinds, so
merging both produces **two authorities that do not recognise each other** —
exactly what #418 §"one source for each fact" forbids.

Verified in this tree:

```sh
sed -n '213,215p' docs/architecture/FLEET-V1-MILESTONE-DELIVERY.md
  # 状态词表（封闭）：DISPATCH_ACK · RUN_ENDED · CI_PASSED · QA_ACCEPTED · FEISHU_DELIVERED
  # OWNER_READ 不在词表里，也不许出现。
grep -oE '"(RUN_COMPLETED|CI_PASSED|PHASE_ACCEPTED|PR_ACCEPTED|TASK_COMPLETED)"' \
     integrations/fleet-v1-milestone-notify/milestone_notify.py                # all five
```

Of #422's five, #423 emits only `CI_PASSED`. Of #423's five, #422 declares only
`CI_PASSED`. The intersection is one value out of nine.

Independently reported by the L1 reviewer on #418 (verdict: #422 REQUEST
CHANGES). Resolving it is **not** this lane's job — either the vocabulary is
aligned or #422 carries a mapping table, and that belongs to #422/#423's authors.

## 4c. The three modules actually compose

Each piece has its own tests, and each of those fakes its neighbours. Nothing
proved that #426's adapter output is what #423's normalizer accepts, or that
#428's observer drives the pair with real collaborators. That seam is where three
individually green PRs can still fail to fit.

`tests/test_fleet_milestone_chain_integration.py` wires the real modules:

```
CloudCliRunSource.read  ->  MilestoneObserver.run_once  ->  MilestoneNotifier
        (#426)                      (#428)                      (#423)
                                                                    |
                                                              FakeLark, injected
```

| Check | Result |
|---|---|
| `#426`'s cloudcli payload key set == `#423`'s `_CLOUDCLI_ENVELOPE` | holds, 11 keys |
| `#426`'s github payload key set == `#423`'s `_GITHUB_ENVELOPE` | holds, 9 keys |
| `normalize("cloudcli", adapter.read(...))` accepts it | yes — the strict closed envelope does not refuse |
| dispatch returns while the run is still `running` | **0 messages** |
| the run turns `completed` on a later tick | **exactly 1 message** |
| restart: new observer, new state file, same ledger | **still 1 message** |
| observer state file lost entirely | **still 1 message** |
| any of the three modules imports a network client or `subprocess` | none |
| the delivered text contains the run's assistant content | no — the adapter reduces it to `PRESENT` |
| `completed` with **no** trusted native output | one message, `outcome=UNKNOWN`, `Severity: ACTION`, `native-output=MISSING`, and the text says *do not treat this as success* |

The last row matters most for #417's security clause: the assistant's words never
leave the device, so a transcript cannot reach the outbound provider even by
accident.

Two readings that are easy to get wrong, and are pinned in the test:

- A completion without trusted native output is **not** silent. Silence would be
  indistinguishable from success to an owner who dispatched work. The honest
  outcome is one actionable `UNKNOWN` message that says so.
- In the observer's report, `state == DELIVERED` means *the message reached the
  provider*. The milestone's own verdict is `outcome`, and that is `UNKNOWN`
  here. Reading `state` as the milestone state would invert the whole rule.

This is CODE + UNIT on one host. It is **not** a deployed observer, not a real
CloudCLI or GitHub client, and not a Feishu delivery.

## 5. BLOCKED — #416 has no V1-only path

`#416` (`compat/l2-cloudcli-141-run-get`) is stacked on `#407`. Merging it would
drag all 85 files of `#407`'s V2 manager-wake scope into the V1 line, which the
owner explicitly excluded.

Taking only #416's own diff (`dc73c600^..dc73c600`, 3 files, +430/−28) does not
work either. Minimal reproduction:

```sh
git diff refs/origin/pr/416^ refs/origin/pr/416 > 416.patch
git apply --check --3way 416.patch      # on main or this integration tree
#   → conflict applying to fleet_mcp/cloudcli_native.py
#   → error: fleet_mcp/run_watcher.py: does not exist in index
```

Three independent reasons, any one of which blocks a backport:

1. **`fleet_mcp/run_watcher.py` does not exist on `main`.** `#407` creates it
   (254 lines). Half of #416 edits a file the V1 line does not have.
2. **`validate_arguments` is a different function.** `main`'s version checks
   required parameters and unknown parameters and stops there. #416's hunk
   assumes `#407`'s `oneOf`/alias machinery. Backporting the alias alone means
   porting that machinery — that is implementing #407's design, not a backport.
3. **The recorded `run_get` schema differs.** `main` records `runId` and
   `waitSeconds`; #416's context has `deliveryId` added by #407.

This drift is already acknowledged in-tree: `tests/test_cloudcli_windows_compat.py`
carries `@unittest.expectedFailure` on
`test_the_recorded_run_get_schema_is_not_narrower_than_the_device`, whose comment
says the fix is on Draft #407 and that it becomes an *unexpected success* when it
lands. That is the correct shape for V1: the limitation ships **declared**, not
silently.

**Handoff:** the minimum repro above goes to #416's author. A V1-only variant
would need to add the `run`/`wait` alias and the `deliveryId` field to `main`'s
existing `validate_arguments` and `NATIVE_INPUT_SCHEMAS` — a genuine port, which
the owning author should decide on, not this lane.
