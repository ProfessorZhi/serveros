# ServerOS Fleet V1 完整交付设计

状态：用户已确认实施（2026-10-27，“实施吧”“继续”）；设计不是实现、安装或上线凭据。

## 1. 用户目标与范围

用户要求补齐整个 Fleet V1 并上线，并明确强调：稳定控制东京 Linux、公司 Windows、Dell Linux 上的 Claude Code 和 Codex 始终是 V1 核心要求。事件通知与自治接续是在此基础上增加的要求。

本轮包含实现、缺陷修复、测试、能力分发对齐、工程解耦、目录迁移、发布和三台目标设备部署。代码与交付工作目录位于用户指定的 D 盘 projects 下。运行数据和凭据沿用各设备受保护的现有位置，不进入源码。

### 必交结果

1. 三台设备 × CC/Codex 六种组合的真实、稳定控制。
2. 任务派发后立即返回 ACK；后台观察终态，事件持久化，飞书通知，指定父工作自动继续。
3. owner 身份与最新方向记录；冲突在途工作可抢占，旧写入者不能继续提交受保护效果。
4. 一个工作项一个当前写入者；幂等、撤权、重启恢复和未知效果对账真实生效。
5. 节点 serverosd 以 C++ 为主收敛为一个受管进程；本机监控和有限自愈在枢纽离线时继续。
6. 设备能力插件、节点运行时、connector、枢纽和指挥侧插件按各自依赖构建与发布。
7. 代码职责、目录、生成产物、安装端与源端版本可解释；发布可回滚，运行可观测。

V2 的职责树、多总管自治组织、OpenAgents 通信、多 IM、自主权限自动扩大、完整 Agent 实体装配不纳入本次实现。保留必要字段与接口，不用预留接口代替 V1 功能。

## 3. 方案与选择

沿用此前向用户说明、用户要求实施的渐进路线：在现有契约上补闭环，拆构建和模块，逐设备切换。

一次性重写枢纽或重排整个仓库会同时改变权限、发布和路径，回归与回滚范围过大。仅增加几个工具则不能满足三机可靠性、自动接续和架构收口。因此采用按接口分批交付、精确版本验收的路线。

本文件的具体重试、观察与验收参数是实施建议，不冒充用户逐项指定。已有 binding 的资源预算、模型和权限优先；不因本轮交付扩大其它账号或项目权限。

## 4. 模块与权威

| 部分 | 职责与目标位置 |
|---|---|
| L0 | `fleet/` 身份拓扑；`workengine/` 工作、lease、epoch、代理控制；ability-management 唯一能力注册 |
| L1 | `serverosd/` C++ 节点守护；迁移期 `runtime/` 中的节点模块 |
| L2 node | `fleet_mcp/node/` 设备 connector，签名协议接 CloudCLI |
| L2 hub | `fleet_mcp/` 协议与工具，`fleet_hub/` 注入账本、事件和运行依赖 |
| L3 | 设备能力组合、薄 adapter、Skill，复用能力仓库固定 revision |
| L4 | 指挥侧插件与 Operator Skills，通过 MCP 使用 hub |
| 产品模块 | 报告、卡片、告警通知移出 runtime；按现有语义形成 `reports/` 等归属 |

工作/授权记录仍只有既有 owner；事件 SQLite 是派发与状态变化的派生记录，不签发 lease、grant 或最终验收。owner 指令作为版本化工作方向记录纳入现有 Work/Agent Control owner，事件只引用它。

`fleet_mcp/` 不反向加载 runtime、MCP adapter 或装配包。迁移补静态与运行时依赖检查。路径迁移不与权限逻辑变更混为一个包。

## 6. 派发、事件与消费

### 派发顺序

当前身份/项目权限检查 → 持久 intent/幂等占位 → provider 调用 → ACK 持久化 → 返回。存在 run_id 的记录供后台观察；没有 run_id 的创建不凭空生成任务完成事件。带队列 ID 的 ACK 在识别真实 Run 前保持待解析。

补 `work_ref`、`parent_ref`、`agent_ref` 为可选字段，进入幂等摘要与审计。旧调用兼容。自动继续和按工作项抢占必须绑定 work_ref 与可信父检查点；没有这些信息的普通会话仍能控制，但不能宣称已有工作级仲裁。

### 收件箱与观察器

复用现有状态根，SQLite 持久化 events、订阅游标、观察任务和消费者投递状态。事件采用单调 seq、稳定唯一 event_id、设备/runtime/session/run/work 引用、派发者与有界摘要。原始 prompt、凭据和完整聊天不进入事件。

观察器使用现有 provider 的定向 Run 读取接口，10 秒、30 秒、2 分钟、10 分钟退避；24 小时仍无法判定则产生 UNKNOWN/需要决定，不误报失败。已 ACK 记录在重启后可重新发现；先记录终态事件，再完成观察任务，崩溃重放靠唯一键去重。UNKNOWN 后晚到的可信终态可追加更正事件，保留原观察记录。

新增 `fleet_inbox`：有界分页、调用者当前设备/项目读权限过滤、每订阅者独立游标。read 与 ack 分离；ack 不得确认未交付范围。过滤掉的条目不泄露内容，返回可继续扫描的游标，不因无权限事件造成无限空页。凭据轮换不能任意继承另一主体的游标。

### 飞书与唤醒

复用现有通知适配器和已有 owner 私聊绑定。完成按项目 5 分钟聚合，失败/需要决定优先投递；测试先用 fixture，真实通知只发 owner 既有获准目标。找不到唯一目标时保留待投递状态并提出精确缺项，绝不猜群聊。

通知与总管各有持久消费记录。网络未知发送结果按现有 outbox/receipt 对账；不能承诺跨不支持幂等的外部渠道严格 exactly-once。已确认 receipt 不重发；无法核实则保留 UNKNOWN 并升级，不能静默丢弃或盲重试。

总管使用东京 serveros 项目的指定 CC Session；按 #406 最新决定，使用生产 admin 创建会话所沿用的默认 DeepSeek 配置，实际模型/模式运行时回读，不写死模型 ID，不跨项目复用。需要新 Session 时在获准项目创建，并把绑定作为私有实例配置。父检查点明确 required children/依赖集合，全部满足后以 checkpoint revision + dependency set 形成唤醒幂等键。唤醒前重验 lease/epoch/grant/current writer；迟到事件不复活取消工作。总管消费检查点与事件决定下游，不把事件服务做成第二个规划器。

## 7. 身份、方向与抢占

Principal 增加 kind（owner/client/agent），由可信认证映射提供。owner 的多个入口映射到同一稳定 owner 身份，同时保留来源客户端；请求参数不能自称 owner。V1 未映射的现有凭据按兼容的 client 处理，不自动升级。

`fleet_directive` 仅 owner 可调用，显式 scope/supersedes，不做自然语言自动推断。方向记录与 epoch/fence 先提交，再 interrupt 对应 Run；部分中断失败逐项记录并重试/升级。旧 writer 从 fence 提交起不能执行新的受保护写入。工具无法撤回已经交给任意原生进程的外部效果；未证实停止的任务不能被标记已停。

正常可达、可中断场景要求 1 分钟内停下并读回；离线场景记录抢占已请求、旧权限已 fence、运行状态 UNKNOWN，必须在恢复测试中证实不会继续旧工作。不能用逻辑标记替代物理中断证据。

## 8. 解耦、构建与目录迁移

沿 #406 的 D1–D10 收口，但以依赖而非目录数作为完成标准：

1. 先拆设备插件与 node-runtime；Skill 变更不得改变 node-runtime digest。再拆 connector/hub 发布依赖闭包。
2. F1/F2 接线稳定后迁 hub 装配、卡片/报告/通知；拆 CLI 保持命令接口。
3. 代理控制移入 workengine，保留既有状态文件与 schema 兼容；不借搬目录迁移运行库。
4. 旧 `mcp/agent_mcp.py` / `fleet/controller.py` / router 逐消费者替换；不能由新面覆盖的功能保留薄适配器。所有 consumer 已迁移才退役重复实现。
5. C++ serverosd 先建立每 unit 唯一恢复者，再按观测→自愈→本地 lease→事实接口接管。每项接管后 Python 对应执行关闭；不能同时运行两个恢复者。统一名称在发布映射准备好后切换。
6. 源/生成插件已有单向生成链继续沿用。实验插件删除复用 #406 已有变更，核对客户端消费者并完成正常升级；历史证据保留可追踪位置。
7. ability-management 保持扁平 stable path，只更改实际需要的 canonical payload、revision 和 distribution，完成受影响消费者读回。
8. 已归档 hwz-ops 的测试依赖迁到明确 fixture 或当前 records 接口；私有生产记录不搬入公共测试。

迁移顺序与 #406 中 D8 改名顺序差异以“先单恢复者、后切换名称”解释，并在实施计划统一。新依赖规则随迁移落地；不只写自然语言约束。

## 10. 验证与上线

### 发布门

1. 受影响模块 TDD：失败用例先证明缺陷，再实现；授权、租约、未知效果不得放宽断言。
2. 精确候选 SHA 的离线/契约测试、依赖守卫、能力 registry、构建可重现与插件检查通过。
3. 整套 hermetic suite 零新增失败；Q2 修完真实 drift，未分类项逐个有理由。仅确需现场的测试转入设备验收；测试顺序污染需修复。
4. Linux/Windows 原生构建与测试通过。现场六组合正反例全部有证据，历史 SHA 的 PASS 不替代当前候选。
5. 事件→通知→总管→下游任务端到端真实走通；owner 抢占、断线恢复、重复投递、撤权和回滚演练通过。
6. 独立审阅通过，遗留项不能包含上述必交能力。

### 发行流程

发布清单固定 ServerOS、ability-management、CloudCLI 来源/版本，以及 Core、connector、hub、设备插件、指挥插件的 digest；包含 schema 兼容范围、前一版本和回滚入口。

先在隔离候选入口验收，复用已绑定的 ingress/身份。东京已经存在活动 Next 服务，先核其 owner、当前用途、活跃消费者与版本；仅在属于本次可切换范围时复用，不能当空白新建现场。先更新一个 Linux 设备验证新旧协议，再第二个 Linux 和 Windows，最后完成主入口切换与全部客户端读回；顺序可按现场活动窗口调整，但不能跳过一台。

部署使用既有 release/install 工具、版本目录及原子 pointer。升级前保存配置/状态的受保护备份和旧二进制，采用兼容的 additive schema；旧版本不能读取的新 schema 必须提供兼容出口或独立状态回退，不盲目将旧程序指向新库。

每次切换检查活动 Run 和恢复者归属。需要停止的既有用户任务先等待安全窗口或请求精确选择；本轮专用验收任务可受控中断。不会通过重启共享宿主解决单个服务问题。

### 对外状态

SOURCE_READY → OFFLINE_PASS → DEVICE_ACCEPTED → DEPLOYED_CANDIDATE → FINAL_ACCEPTANCE。
